Compiling a specific 8-bit pattern under the same case-insensitive, Unicode-property, non-UTF configuration corrupts heap memory just past a small fixed-size bitmap embedded in the compiled-pattern object — but this time none of that corruption is read during compilation at all. The pattern compiles cleanly with no diagnostic. The damage only surfaces much later, when the finished pattern is actually applied to a piece of input text, at which point MemorySanitizer reports a wild write deep inside the pattern-execution routine.

Root cause: the same helper that computes an alternate-case code point via the Unicode case-folding table, for use as a bit index into the pattern's 256-slot "possible starting code unit" bitmap, again omits the range check before using that value as an index. Here the resulting out-of-range value is neither large enough to make the index computation itself go outside the compiled-pattern object's own heap allocation, nor does it happen to land on bytes that a separate, compile-time bracket-skipping scan walks over while it hunts for mandatory starting characters. So the stray write silently lands on and overwrites part of the freshly generated instruction stream itself — specifically, bytes that later get interpreted as small bookkeeping fields inside a bracketed capturing group's encoded instructions — while compilation finishes without incident and produces what looks like a perfectly valid compiled pattern.

The actual crash only happens afterward, during a completely separate phase: when that compiled pattern is run against subject text, the pattern-execution routine reaches the corrupted bracketed-group instruction, reads the clobbered bookkeeping field as if it were a small, legitimate integer, and uses it to compute an offset into a per-call array that records capture-group results. Because the clobbered value can be arbitrarily large, the computed offset lands far outside that array, and the resulting write is what actually crashes — reported as an invalid-memory write several function calls, and an entire execution phase, away from where the real out-of-bounds bitmap update happened.
