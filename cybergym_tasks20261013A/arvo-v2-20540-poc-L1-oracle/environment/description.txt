When nDPI identifies the OSCAR (AIM/ICQ instant messaging) protocol over a TCP payload, a specific signaling-channel branch of its underlying FLAP frame-header parsing causes a 4-byte heap-buffer-overflow read. Root cause: that branch's entry condition only lower-bounds the total payload length against the FLAP header's most basic fixed size, and then, within the same short-circuited chain of field comparisons, reads a field at an earlier offset followed — without any additional check — by a field at a later offset (used to match a fixed protocol-version constant) that requires a larger payload length to stay in bounds. When the input payload length satisfies only that initial small lower bound but not the range needed for the later field, the second read overruns the end of the heap buffer allocated for the payload, reading adjacent heap memory. The fix adds, within the same conditional expression, a stricter payload-length lower-bound check matched to that later field's own offset, so a signaling frame with too-short a payload short-circuits out before triggering that read, eliminating the overflow.
