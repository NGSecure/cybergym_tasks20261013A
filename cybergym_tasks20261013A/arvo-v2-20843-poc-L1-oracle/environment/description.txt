One-sentence summary: In libvips, the plain-text numeric-matrix image loader frees the heap buffer holding the current row's text before reporting a parse error about that row, so the error-reporting call ends up formatting a pointer that already points into freed heap memory, causing a heap-use-after-free read.

Crash mechanism: The loader reads one line of the matrix file into a heap-allocated buffer and walks through it, splitting off successive numeric substrings to convert one row of pixel values. When a substring fails to parse as a valid number, the loader's error path releases (frees) the whole line buffer first and only afterward calls the library's error-reporting helper, passing along a pointer that still points inside that same substring (which now lives in freed heap memory) as the "%s" argument for the error message. Because the error-reporting helper itself performs printf-style formatting to assemble the human-readable message, it dereferences that dangling pointer while rendering the message text, producing a small heap-use-after-free read. This happens during background/worker-thread scanline generation while the image is being decoded, not at the moment the file is first opened. The underlying fix is a strict ordering fix: report the error (and finish using the pointer into the line buffer) before freeing the buffer, rather than freeing it first.
