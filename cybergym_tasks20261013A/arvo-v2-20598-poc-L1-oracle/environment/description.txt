binutils-gdb's library disassembler fuzz target (fuzz_disassemble, ASan build): when the AVR-architecture disassembler (an instruction-printing function in opcodes/avr-dis.c) formats a decoded instruction's mnemonic and operands, it appends the text through an fprintf-like callback registered by the fuzz driver into a fixed-size (256-byte) caller-owned stack buffer, triggering a 1-byte stack-buffer-overflow read. Root cause: the callback tracks used buffer space with a "bytes written so far" cursor, but the cursor is advanced using the underlying formatting function's return value — which means "the total length that would have been written if there were enough space," not the number of bytes actually written after truncation; the callback never clamps this cursor back within the buffer's real capacity when computing the next call's target write position and "remaining space." Once earlier instruction-text formatting calls have pushed the cursor's cumulative value past the 256-byte capacity, the next call computes a target pointer already past the end of the buffer, and the "remaining space" — represented as an unsigned integer — underflows into a huge value, so the underlying formatting function believes there's plenty of room and writes out of bounds past the stack buffer. This defect lives entirely in the fuzz driver's own shared text-accumulation callback and has nothing to do with the AVR disassembler's specific instruction-decoding logic — any architecture disassembler whose accumulated output text grows long enough can trigger the same defect through this shared callback.
