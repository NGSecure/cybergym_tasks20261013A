Compiling a specific 8-bit pattern makes PCRE2's pattern-analysis pass touch memory outside a small fixed-size bitmap embedded in the compiled-pattern object, and this time AddressSanitizer catches the invalid access at the exact statement that causes it, rather than at some later, unrelated piece of code.

Root cause: when a pattern is compiled with case-insensitive matching plus Unicode property support enabled, but without full UTF interpretation, one helper computes the alternate-case code point of a character via the Unicode case-folding table and uses that value, unchecked, as the bit index into the pattern's built-in "possible starting code unit" bitmap, which only has 256 slots. Setting a bit in that bitmap is not a single atomic instruction: it is a compound read-modify-write — the byte at the computed table offset is first read, then a bit is toggled in it, then the byte is written back. Because this caseless-plus-Unicode-property, non-UTF code path never range-checks the alternate-case value against the bitmap's 255-slot limit, an alternate-case value that lands enormously outside that range produces a table offset so far removed from the compiled-pattern object's own heap allocation that even the initial read half of that compound update already falls on memory nowhere near anything belonging to this object. The sanitizer reports a one-byte out-of-bounds read right there, at the very statement performing the (attempted) bit update.

That distinguishes this crash from a related one in the same area: when the same missing check instead produces only a modestly out-of-range value, the read-modify-write can silently succeed within the bounds of the same heap block, quietly corrupting adjacent bytes without faulting at all, and any resulting crash only appears much later, in an unrelated piece of code that eventually reads that corrupted region. Here, in contrast, there is no adjacent-memory corruption and no downstream consumer involved — the out-of-range index is large enough that the very operation performing the flawed table update is itself what goes out of bounds, so the reported crash site and the true defect are the same statement.
