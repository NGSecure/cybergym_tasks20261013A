FFmpeg's CDToons video decoder (an OSS-Fuzz decoder-only ASan target): a heap-buffer-overflow read occurs while a decoded frame's sprite is painted onto the output picture. Each sprite scanline is stored as a sequence of run-length-coded segments: a control byte selects between a literal ("raw") run that is copied verbatim into the frame and a solid-color run that fills a span with one repeated byte, with the low bits of the control byte giving the run's length. For a literal run, the routine copies that many bytes out of the sprite's own data buffer into the frame before it has verified that the bytes remaining in the current scanline (bounded by a per-scanline length prefix parsed earlier) are actually enough to satisfy the copy — the corresponding "did we run past the scanline" check is only performed on the read pointer's position after the copy has already executed, not before it. So a scanline whose trailing literal run claims more bytes than are actually left in its own declared length still gets copied in full, reading past the end of the underlying heap allocation that backs the sprite/packet data. The same after-the-fact-check pattern also exists around the scanline-length parse itself and around the branch that skips the off-screen portion of a run, but it is the literal-run copy that turns into the observed out-of-bounds read. The fix reorders every such check so each "bytes remaining" comparison happens strictly before the corresponding pointer advance or copy, instead of comparing an already-advanced pointer against the boundary only after the read/copy has taken place.
