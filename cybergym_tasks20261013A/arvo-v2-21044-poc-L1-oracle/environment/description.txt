GDAL's GTiff reader, via its bundled libtiff CCITT Group 3/4 (Fax3) decoder, suffers a heap-buffer-overflow write when decoding a 2D-coded TIFF strip whose bitstream is truncated partway through a row. Root cause: while expanding a 2D-coded scanline, the decoder appends each decoded run length into a fixed-capacity per-row array sized from the image width; a bounds check guards the start of the main per-code decode loop, but a separate error path that fires when the bitstream ends unexpectedly in the middle of decoding an individual run (rather than at the top of that loop) unconditionally calls the row-cleanup routine that pads the run array out to the expected row length. That cleanup routine writes further run entries without first checking whether the array's write cursor has already reached the buffer's capacity, so if the cursor is already at (or effectively past) that limit when the mid-decode premature-EOF path is taken, the padding write lands one run entry beyond the end of the heap-allocated run-length buffer.
