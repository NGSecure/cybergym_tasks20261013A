One-sentence summary: nDPI's packet-processing engine suffers a small heap-buffer-overflow read when it handles an IPv6 packet whose captured length is too short to actually contain a full IPv6 header.

Crash mechanism: The workflow that turns a raw captured packet into a flow record determines the IP version and, for IPv6 traffic, hands off a pointer into the packet buffer (positioned at the start of what should be the IPv6 header) to a helper that builds an internal flow-info structure from that header. That helper unconditionally dereferences fields near the tail end of the IPv6 header -- specifically the destination-address words -- to derive an internal (v4-style) representation of the address and to read the next-header/payload-length fields. The problem is that nothing on the calling path first confirms that the packet's actual captured length (as reported by the capture metadata) is large enough to cover the IP-header offset plus the full size of an IPv6 header before this dereference happens. When a packet is captured/truncated such that fewer bytes were actually captured than the offset-plus-header-size requires, the helper still reads as if the full header were present, walking a few bytes past the end of the heap allocation backing the captured packet data. AddressSanitizer flags this as a small (4-byte) out-of-bounds heap read immediately past the end of the allocated packet buffer. The fix adds an explicit length check on the IPv6 branch of the packet-processing routine -- before the IPv6-header pointer is set up and handed to the flow-info helper -- that bails out early ("packet too short") whenever the captured length does not cover the full IPv6 header at that offset, so the helper is never invoked against a truncated buffer.
