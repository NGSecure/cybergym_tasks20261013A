When ImageMagick renders annotation text (rasterizing glyphs onto a canvas), it reads a glyph bitmap obtained from FreeType under an incorrect assumption about its pixel data, triggering a 1-byte heap-buffer-overflow READ. Root cause: the rendering logic only distinguishes "monochrome bitmap" from "everything else," treating any non-monochrome glyph bitmap as a standard 8-bit grayscale bitmap and computing each pixel's index via "pitch × row + column"; but FreeType defines more pixel formats for glyph bitmaps than just those two, and when a given glyph's actual rendered bitmap is one of the other formats, its true row pitch doesn't match the assumed 8-bit grayscale layout, so the index — incrementing with the column in the loop — runs past the heap memory actually allocated for that bitmap this time, reading an unallocated byte immediately beyond it. The fix replaces this implicit two-way branch with an explicit three-way one: only read pixels via the grayscale formula when the bitmap is confirmed to actually be standard 8-bit grayscale; only read via the bitmask formula when it's confirmed to actually be monochrome; for any other pixel format, use a default opacity value and don't access the bitmap data at all, eliminating the condition that triggered the out-of-bounds read.
