nDPI's packet-classification workflow entry point, invoked by the fuzz_ndpi_reader harness for every fuzzer-supplied raw packet, suffers a 2-byte heap-buffer-overflow read while decoding a UDP-encapsulated tunnel candidate. Root cause: once the workflow has parsed the IPv4/IPv6 header and determined the next-layer protocol is UDP with tunnel decoding enabled, it computes the offset just past the IP header and immediately casts the packet buffer at that offset to a UDP header structure, reading its source/destination port fields to look for known tunnel signaling ports — without first verifying that the packet's actual captured length extends far enough past the IP header to contain a complete UDP header. A guard that would reject a packet too short to hold a full UDP header at that point exists in the source but is wrapped in a preprocessor conditional that is not enabled in this build, so it never executes. Consequently, a captured/crafted packet whose IP header leaves fewer bytes remaining in the allocated packet buffer than the size of a UDP header causes the port-field read to run past the end of that buffer.
