GNU binutils' opcodes library crashes with an MSan use-of-uninitialized-value while disassembling an H8/300 instruction stream.

The H8/300 disassembler copies the raw instruction bytes into a fixed-size stack buffer through a loop of small, length-limited reads from the input, tracking in a separate counter how many bytes it believes it has successfully obtained so far. When the supplied instruction stream is shorter than the disassembler's maximum instruction length, that counter is advanced even for a read that did not actually succeed, so it ends up describing more of the stack buffer as populated than what was truly copied in. A later stage that walks the opcode table to identify and decode the instruction trusts this counter as the bound on valid buffer contents and reads from the buffer up to that bound without any other check that each byte was actually written, so decoding a short/truncated encoding pulls uninitialized stack bytes into the instruction-matching logic. This is a pure decoder-side bookkeeping bug in the length calculation, not a memory-safety issue in how the input itself is parsed.
