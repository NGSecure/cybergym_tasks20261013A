nDPI's post-detection protocol-category assignment logic reads an SSL/TLS-specific field of a per-flow union before confirming that the flow was actually parsed by the TLS detector, causing a use of uninitialized memory when a different protocol detector populated the same union storage instead.

Crash mechanism: the routine that assigns a traffic category once protocol detection has finished, invoked at the tail end of the main per-packet detection entry point, checks flow->protos.stun_ssl.ssl.client_requested_server_name[0] to decide whether to look up a custom category for the SNI hostname. This field lives inside flow->protos, a union shared by multiple protocol detectors, each of which writes its own protocol-specific layout into the same backing memory once it recognizes a flow. When a flow is instead recognized by a non-TLS detector (that detector copies its own protocol state into flow->protos without ever touching the TLS/SSL member of the union), the bytes that would back client_requested_server_name are left unwritten. Because the category-assignment routine performs this check unconditionally, it reads this never-initialized region regardless of which protocol actually matched, which MemorySanitizer flags as a use-of-uninitialized-value at the read of that field.

The upstream fix adds a precondition: the check is now guarded by flow->l4.tcp.tls.hello_processed == 1, so the SSL/TLS union member is only dereferenced when the TLS parser actually ran and populated it for this flow, closing the union type-confusion gap.
