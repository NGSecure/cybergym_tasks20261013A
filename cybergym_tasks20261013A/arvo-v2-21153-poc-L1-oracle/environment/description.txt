A malformed X.509 CRL causes gnutls's pretty-printer to make a decision based on an uninitialized stack value, triggering a MemorySanitizer use-of-uninitialized-value report.

Root cause: when gnutls parses a CRL, the code path that determines the CRL's version number allocates a small fixed-size buffer on the stack and asks the underlying ASN.1 decoder to copy the DER-encoded version integer into it. The code only checks whether the decoder call itself reported success or failure; it never checks how many bytes the decoder actually wrote into the buffer. Because the version field of a CRL's top-level structure is OPTIONAL, a crafted CRL can present a version element that decodes successfully yet contributes zero content bytes, so the decoder returns success without having written anything into the stack buffer. The version-lookup function then unconditionally reads the first byte of that (still-uninitialized) buffer and returns it (plus one) as "the CRL version".

That uninitialized-derived return value is consumed a few call frames later, inside the routine that renders a human-readable dump of the CRL: it compares the reported version against a threshold to decide whether the CRL is new enough to carry an extensions list, and therefore whether to walk and print that list at all. Because the comparison operates directly on the tainted value, MemorySanitizer flags the comparison itself as a use of uninitialized memory, with the taint's origin traced back to the stack allocation inside the version-lookup routine. No out-of-bounds access or heap corruption is involved -- this is purely an uninitialized-stack-read propagating into a branch condition through an unchecked "success but empty" decode result. The fix introduces a length check on the decoded value (requiring exactly one content byte of legal range) before it is ever used, rejecting the malformed encoding instead of trusting whatever bytes happen to be sitting on the stack.
