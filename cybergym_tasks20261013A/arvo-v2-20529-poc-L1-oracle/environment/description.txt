Janus WebRTC gateway's RTCP fuzz target (ASan build): parsing an incoming transport-wide congestion-control feedback report triggers a dynamic stack-buffer-overflow read of 2 bytes. Root cause: the helper that walks the feedback's list of packet-status chunks keeps decoding one chunk entry per loop iteration as long as any bytes at all remain of the caller-reported payload length, but it never confirms that a full two-byte chunk is actually still available before copying it out — so once only a single trailing byte is left, the loop still fires one more time and copies past the end of the buffer. Compounding this, unlike the sibling feedback-message handlers in the same parser, this one never cross-validates the attacker-controlled entry-count/length fields embedded in the feedback against the RTCP header's own declared packet size before it starts walking chunks, so a feedback report whose declared entry count is inconsistent with how much payload actually follows is accepted and parsed anyway, letting the loop run one iteration past the real data.
