jbig2dec (ASan build, libFuzzer harness): decoding a JBIG2 generic region whose arithmetic-coding parameters set the adaptive-template pixel positions to non-default (non-"standard") offsets can trigger a 1-byte heap-buffer-overflow read just past the end of the freshly allocated output bitmap. Root cause: the generic-region decoder splits each row into a "safe interior" and "needs bounds checking" zone by computing, once per region, a margin derived from (a) the requested adaptive-template pixel offsets and (b) a fixed lookahead width needed by an unrelated same-row optimization helper, then subtracting that margin from the region's pixel width using unsigned 32-bit arithmetic to get the right-hand cutoff column. For a region whose width is smaller than that (deliberately inflated) margin, the subtraction underflows and wraps around to a huge unsigned value, so the per-pixel check meant to gate the fast, non-bounds-checked neighbor-pixel accessor is defeated for the whole row: the decoder believes every column is safely inside the interior zone and takes the unchecked path, which reads one adaptive-template neighbor pixel whose computed offset actually lands one byte past the end of the bitmap buffer. The read is single-byte and read-only; nothing is corrupted, but ASan flags the out-of-bounds access.
