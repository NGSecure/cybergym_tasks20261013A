wabt's `wasm2wat` fuzz target reads a crafted WebAssembly binary whose custom "linking" section symbol table contains a symbol-table entry for a function. When wabt's binary-to-IR reader processes that entry, it takes the function index embedded in the symbol record and uses it directly to index into the module's internal vector of parsed functions, without first checking that the index is within range of the number of functions the module actually declares. Because the linking-section index is fully attacker-controlled and the reader trusts it unchecked, an index far larger than the function count causes the vector-index computation to land far outside the vector's backing allocation; AddressSanitizer reports this as an 8-byte heap-buffer-overflow read of a "wild pointer" (an address ASan cannot associate with any known heap chunk), aborting the process. The fault is reached while parsing the custom "linking" section's symbol subsection, inside the callback that materializes a function-symbol entry into the in-memory module representation -- i.e. deep in binary-to-IR conversion, not in low-level byte decoding.

The upstream fix adds an explicit bounds check on the symbol's function index before it is used to index into the functions vector, rejecting the module with a parse error instead of performing the out-of-bounds access. The same commit applies the identical missing-bounds-check pattern to three sibling code paths that handle the other kinds of linking-section symbols, each of which had the same unchecked-index-into-vector bug.
