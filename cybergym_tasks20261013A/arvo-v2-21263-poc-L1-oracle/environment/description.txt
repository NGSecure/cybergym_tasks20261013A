nDPI's DNS protocol detector, while validating that a candidate DNS payload's question-name field is syntactically well-formed, scans forward through the payload looking for the null byte that terminates the encoded domain name, then advances one position past that point and inspects the byte sitting there to decide whether a second, more thorough label-scanning loop should run. That single lookahead inspection dereferences the payload at the advanced position without first checking whether the position still lies inside the payload buffer; only the loop that potentially runs afterward bounds its own scanning index against the payload length correctly. A DNS-labeled payload whose question-name bytes extend all the way to, or just short of, the very end of the allocated payload — such that the advanced lookahead position lands exactly at or beyond the buffer's end — causes this one unchecked byte inspection to read one byte past the allocated buffer, a 1-byte heap-buffer-overflow read. The defect is confined to that single unchecked lookahead byte gating entry into the secondary loop, not to the loop's own (already-correct) bounds checking, and it is unrelated to the SSH, FIX, or Yahoo-Messenger detectors' parsing logic elsewhere in the same codebase.
