OpenSSL's TLS client-side handling of a server's ephemeral Diffie-Hellman key-exchange message contains a heap use-after-free caused by a double free of the same DH key-parameter object.

While parsing the DHE parameters carried in a ServerKeyExchange message, the client handshake logic allocates a raw DH parameter object and then wraps it inside an EVP_PKEY container; wrapping it this way hands ownership of the raw object over to the EVP_PKEY container, which becomes responsible for freeing it later. The code, however, keeps its own separate raw pointer to that same DH object and does not clear it once ownership has been transferred. If a later check on the received parameters (a minimum key-strength/security-level check applied to the negotiated DH parameters) then rejects them, the function jumps to its shared error-cleanup path. That cleanup path unconditionally frees the DH object twice: first directly, through the stale raw pointer that was never cleared, and then a second time indirectly, when it frees the EVP_PKEY container, whose own destructor also frees the DH object it owns. The first free returns the underlying heap block to the allocator; the second free then writes into a reference-count field that lives inside that already-freed block, corrupting freed heap memory with a small (4-byte) out-of-bounds write.

A malicious or malformed TLS server can reach this path by sending a ServerKeyExchange message whose DHE parameters parse successfully but are weak enough (or otherwise fail the security-level check) to be rejected on the subsequent strength check, driving the client into the double-free error-handling path described above.
