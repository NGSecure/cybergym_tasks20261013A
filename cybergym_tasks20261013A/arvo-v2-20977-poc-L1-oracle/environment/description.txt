Rendering a crafted PostScript document with libspectre causes a 4-byte heap-buffer-overflow write inside Ghostscript's in-memory "display" rendering backend, right after the backing bitmap is allocated for the page.

libspectre derives the raster device's pixel width and height from the document's page geometry and passes them straight through to Ghostscript as fixed device dimensions before any page content is interpreted. Ghostscript uses those dimensions to compute how many bytes the backing bitmap needs (row width rounded up to an alignment boundary, times the number of scanlines) and allocates that buffer up front. Immediately afterward, before the PostScript program body runs, Ghostscript clears the freshly allocated bitmap by filling the whole page rectangle through the true-color (32-bit-per-pixel) scanline-fill path, writing one 32-bit word per pixel per row.

With a suitably crafted page geometry, the row-width value used when sizing the allocation and the row-width value used when walking pixels during the fill end up inconsistent by a small amount, so the last scanline's fill loop writes one 32-bit pixel past the end of the buffer that was just allocated for it. AddressSanitizer catches this as a 4-byte out-of-bounds heap write immediately adjacent to the allocation, occurring while the display device is still being opened/initialized, well before any PostScript drawing operators from the document are executed.

The upstream fix is not a change to libspectre's own C sources; it is a bump of the vendored/embedded Ghostscript version used to build libspectre, to a release where this rendering backend's bitmap-sizing and scanline-fill logic were substantially reworked, which eliminates the size mismatch. No PostScript-level operator or specific numeric geometry value is disclosed here.
