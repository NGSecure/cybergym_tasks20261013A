While parsing the ALPN (application_layer_protocol_negotiation) extension inside a TLS ClientHello, nDPI's TLS handshake parser walks a list of protocol-name entries using a running offset that is only bounded against a 16-bit "total ALPN block length" field taken from inside the extension itself, never against the actual size of the reassembled handshake record. Root cause: every other extension branch handled by this parser checks the parsing offset against the record's real length before reading further, but the ALPN branch's loop condition omits that check, so when the attacker-controlled ALPN length field claims more bytes than the record actually contains, the loop keeps advancing past the end of the data nDPI actually received into the unwritten tail of the heap buffer allocated for TLS message reassembly. The stale bytes read from that unwritten region are then used as an entry-length value in a subsequent bounds comparison, so the comparison result is computed from memory the parser never initialized.
