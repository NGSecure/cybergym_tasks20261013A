ImageMagick's built-in synthetic-gradient image decoder crashes with a 1-byte out-of-bounds stack read while parsing an embedded "start-color[-stop-color]" specification that it copies into a fixed-size, MagickPathExtent-length stack buffer from the pseudo-filename passed to the reader. Root cause: the decoder scans that buffer character by character looking for the '-' separator between the two colors; whenever it meets an opening parenthesis (used to wrap a color's numeric/parametrized form) it drops into a nested loop that advances until it finds the matching closing parenthesis or hits the string's terminating NUL byte. That nested loop, on its own, always stops safely in-bounds. The bug is in what happens next: once the nested loop returns control to the outer scan, the outer loop still performs its own per-iteration pointer advance and then re-dereferences the pointer to test its own exit condition, with no check for whether the nested loop had actually stopped due to running out of string (an unterminated/unbalanced parenthesis group) rather than finding a real separator. Because the color-spec text is copied into the fixed-size stack buffer with truncation, the copy's terminating NUL lands exactly at the buffer's last valid byte whenever the source text is at least as long as the buffer, so that extra unconditional pointer advance and dereference walks one element past the end of the stack array — the observed one-byte overflow read. The fix wraps the nested parenthesis-skipping loop in a block and, immediately after it, explicitly tests whether the loop exited because it hit the terminating NUL (i.e., no closing parenthesis was ever found) and, if so, breaks out of the outer scan loop right away instead of letting it fall through to its normal increment/re-check step — closing exactly the missing-termination-check gap that let the scan step past the buffer. Verified as directly on point: the crash's own reported function is the one patched, at the very statement the diff wraps, so no vendored/third-party dependency is involved. The identical color-parsing loop (copy-pasted, with the identical off-by-one gap and identical fix) also existed in two of the project's own command-line argument-parsing code paths for the same start-color/stop-color syntax, but those are separate call sites from the one that actually crashes here.
