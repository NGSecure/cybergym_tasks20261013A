nDPI's packet-classification pipeline (ASan libFuzzer target, driven through the pcap-style packet reader) hits a heap-buffer-overflow read while dissecting a UDP datagram whose source or destination port matches the TZSP tunneling protocol port. Root cause: once the TZSP branch is entered, the code immediately reads several fixed-position header fields (a version byte, a type byte, and a following two-byte "encapsulated protocol" value) directly out of the captured-packet buffer at an offset computed from the IP/UDP header lengths, without first checking that the packet's actual captured length is long enough to contain those bytes past the UDP header. When the input packet is crafted so its captured length ends right at or before that computed offset, this read walks a few bytes past the end of the heap buffer that holds the raw packet data, which ASan reports as a small out-of-bounds read. The fix adds an explicit length check comparing the captured packet length against the offset plus the size needed for the version/type/encapsulated fields, returning early (treating the packet as not TZSP) whenever the packet is too short, before any of those fields are dereferenced.
