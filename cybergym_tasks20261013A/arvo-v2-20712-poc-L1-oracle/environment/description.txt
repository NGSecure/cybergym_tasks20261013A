nDPI's DNS protocol dissector (fuzz target fuzz_process_packet, ASan build) has a heap-buffer-overflow read while parsing the answer-record section of a DNS reply packet. Root cause: for each answer record, the parser first walks the record's (possibly compressed) name to compute how many bytes to skip, advances its cursor into the packet by that computed amount, and then immediately reads a following two-byte field describing the record's type. The name-length computation is driven by attacker-controlled length-prefixed label bytes and can return a length far larger than what actually remains in the packet, since it derives from a single length byte (up to a couple hundred) rather than from how much data the packet truly still has; the code advancing the cursor by this length never re-checks the cursor against the real end of the payload before the following two-byte read dereferences it. A DNS reply whose answer section encodes an oversized name/label length can therefore push the cursor arbitrarily far past the end of the allocated packet buffer, so the subsequent two-byte read lands on unrelated heap memory (or entirely unmapped memory) well outside the buffer's actual bounds, rather than merely a few bytes past its end. The fix inserts a bounds check (the cursor plus the size of that following field must still be less than the packet's payload length) immediately before that read, aborting answer-record parsing on out-of-range input instead of dereferencing past the buffer.
