ImageMagick (MSan build): reading a LABEL image whose caption text embeds a "%[pixel:...]" property runs the property's argument through the FX (image-calculator) expression interpreter, once per RGB channel (red first). The triggering FX text is the "while(condition,expression)" control-flow function with both the condition and the loop body left empty. The while-handler splits the argument on its one comma into a "condition" part and an "expression" part, then loops: evaluate "condition", and only if that result is non-zero does it go on to evaluate "expression" and assign that result into an accumulator variable — which is the enclosing function's own top-level local, declared without an initializer. With an empty condition, the inner evaluation safely short-circuits to 0.0 (the interpreter has an explicit empty-string guard, so this is not an out-of-bounds or indeterminate-byte read), and since 0.0 is below the loop's epsilon threshold, the loop's break fires on its very first pass — before the line that evaluates "expression" and assigns the accumulator is ever reached. The function then returns that accumulator anyway, and because this loop was its only assignment site anywhere in the function, what gets returned is whatever indeterminate value happened to already be sitting in that stack slot. That garbage double is returned as the FX result for the pixel's red channel, copied wholesale into a PixelInfo struct a few calls later during color-name lookup, and only "used" — and flagged by the sanitizer — many frames further on, when the color-tuple/SVG-compliance code rescales that still-uninitialized red channel to a byte value; the crashing frame and the frame that actually left the value uninitialized are consequently far apart in the call stack. Two structurally identical FX control-flow constructs, "do(action,condition)" and "for(init,condition,action)", have the same missing-initializer hazard for their own accumulator, even though this particular PoC only exercises "while".
