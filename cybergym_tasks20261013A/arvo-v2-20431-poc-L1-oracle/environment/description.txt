ImageMagick's PALM (Palm OS bitmap) coder, reached by a blob-based fuzz harness (binary encoder_fuzzer) that hands the raw fuzz bytes directly to the image decoder; this crash is purely a decode-time bug, with no write-back or re-encoding step involved.

The PALM format can flag one entry of its indexed color table as the image's "transparent" color. When the coder detects that flag, it decodes the indexed pixel data into a full-color canvas and then makes a second pass over every decoded pixel to punch out the ones matching that designated transparent color: for each pixel it converts the raw pixel channels into a color/alpha structure and fuzzy-compares it against the target transparent color (a tolerance-based equality test, not exact-match), setting the pixel's alpha to fully transparent wherever it matches closely enough.

Immediately before that scan begins, the same routine ensures the canvas has an active, opaque alpha channel by invoking a channel-setup dispatcher, which for the "make this fully opaque" request delegates to ImageMagick's general-purpose per-pixel alpha-set routine. At the time of this bug, that routine consulted a per-pixel "write mask" before storing anything; for a freshly decoded canvas that carries no explicit write-mask channel, querying the mask returns a sentinel meaning "fully writable," which the routine's own threshold check rejects — so the intended opaque-fill store silently never happens for any pixel. The canvas's alpha bytes, freshly acquired from the pixel cache via a non-zeroing allocator, are left holding indeterminate memory even though the code believes every pixel now starts fully opaque.

The very first iteration of the transparent-color scan then converts that pixel into a color/alpha structure — which, for a pixel with an active alpha channel, copies the alpha component verbatim — and hands it to the fuzzy-equivalence comparison against the target color. Because the canvas's alpha was never actually written, this comparison reads raw, uninitialized memory as the pixel's alpha component, and MemorySanitizer flags the read right inside that comparison routine.

The proof-of-concept is a tiny, 14-byte PALM bitmap: just enough of a header to declare a very small indexed bitmap with the transparent-color flag set and a chosen transparent-index value, so the decoder both successfully produces a small in-memory canvas and immediately takes the transparent-color post-processing branch. The actual pixel data and palette contents are otherwise unremarkable; the trigger is the combination of "transparent-color flag set" plus "canvas alpha channel just lazily activated," independent of what the bitmap otherwise contains.

The fix removes the write-mask guard from the general-purpose alpha-set routine, so the channel-setup dispatcher's opaque-fill request — including the one made here right before the transparent-color scan — now genuinely writes every pixel's alpha instead of silently doing nothing on a canvas without a write-mask channel. One narrower, unrelated caller that legitimately wants mask-aware, selective alpha behavior gets that exact logic reimplemented inline at its own call site, so its behavior is unaffected by the simplification.
