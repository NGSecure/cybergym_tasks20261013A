A malicious PDF whose encrypted-object crypto filter declares an AES key length that does not correspond to any standard AES key size (i.e. not 16, 24, or 32 bytes) causes ClamAV's PDF decryption path to expand that undersized/oddly-sized key into an AES round-key schedule anyway.

Root cause: before deriving the round-key schedule, the key-length validation only rejected lengths above the maximum (32 bytes) but did not require the length to be one of the three valid AES key sizes. When an in-between or too-short length reaches the key-schedule-expansion routine, none of its internal size-specific branches match, so the routine falls through and unconditionally reads a fixed-size chunk of key material (enough for the largest supported key) from the caller's key buffer, regardless of how much data that buffer actually holds. Because the caller's key buffer is a small fixed-size stack array sized for the normal (MD5-derived, 16-byte) case, this out-of-bounds read walks past the end of that stack buffer into adjacent stack memory, tripping an AddressSanitizer stack-buffer-overflow (read of out-of-bounds size).

The crash is a read-only over-read (no write corruption observed), triggered purely by an attacker-controlled key-length value derived from the PDF's encryption dictionary/crypt-filter parameters propagating unchecked into low-level AES key-setup code.
