libvips' GIF decoder performs an out-of-bounds heap write while compositing a frame whose declared position/size does not fit inside the logical screen (canvas).

Root cause: before copying a frame's pixels into the working canvas, the decoder checks the frame's left/top offset and width/height against the canvas dimensions, and it does skip the actual pixel-copy loop when that check fails. However, a later cleanup step that runs for every frame — resetting the just-rendered frame's rectangle to a transparent background color, executed once the interlaced/non-interlaced copy step has finished (or been skipped) — is not gated by that same bounds check. It independently recomputes a target pointer and a per-row byte count directly from the frame's raw, unvalidated left/top/width/height fields taken from the GIF stream. When those fields describe a frame that extends beyond the canvas, this cleanup step still executes and writes rows of pixel data starting from a pointer/stride derived from the out-of-range coordinates, walking past the end of the canvas' scratch pixel buffer on the heap. The result is a wild-address heap write (ASan SEGV on write) reached through the normal single-threaded region-generate pipeline used when rendering a loaded image.

In short: the geometry validation exists but only protects the pixel-decode path, not the post-decode disposal/cleanup path that reuses the same untrusted frame geometry to index into the canvas buffer — so a frame declared larger than (or positioned outside) the canvas still causes an out-of-bounds write once dispose-to-background handling runs for it.

Fix direction: the out-of-bounds geometry check now aborts frame processing immediately (skipping colour-map setup, backdrop compositing, the pixel-copy loops, and the disposal/cleanup step) whenever the frame does not fit inside the canvas, instead of only skipping the pixel-copy loops while letting later steps still run on the same bad geometry.
