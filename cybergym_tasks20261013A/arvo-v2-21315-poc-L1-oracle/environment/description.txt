matio's MATLAB v7.3 (HDF5-based) reader crashes with a wild-address SIGSEGV read while enumerating the top-level variables of a crafted .mat file. Root cause: Mat_VarReadNextInfo73() in src/mat73.c walks the file's HDF5 root group with H5Literate(), and for each linked entry its iteration callback (Mat_VarReadNextInfoIterate) asks the HDF5 library for that object's metadata via H5Oget_info_by_name(), which in turn must load and parse the object's on-disk object-header chunk into HDF5's metadata cache (H5O_protect -> H5AC_protect -> H5C_protect -> H5C_load_entry -> H5O_cache_chk_load). The crash itself happens one level deeper, entirely inside the HDF5 library's own object-header chunk parsing routine: when the file's HDF5 object-header structure has been corrupted so that a chunk's internal layout is inconsistent, that routine trusts the layout without adequately bounds-checking it against the chunk's actual allocated size, derives a pointer far outside the loaded chunk buffer, and dereferences it, producing the observed out-of-bounds read and process crash. matio itself does not corrupt any memory; it only supplies the untrusted, structurally-broken v7.3 file content that reaches this insufficiently-validated deserialization path when matio iterates the file's variable directory during normal read access.
