ImageMagick's TIFF decoder (exercised through the Magick++/libFuzzer TIFF round-trip fuzz target, MemorySanitizer build) reports a use-of-uninitialized-value while importing a strip-organized CMYK image whose samples are stored as 32-bit IEEE floats. Before reading a strip's raw bytes from the file, the decoder allocates a scratch buffer sized a few bytes larger than the strip's exact encoded byte length — the extra slack exists so the per-sample pixel importer can safely consume a whole 4-byte quantum even when it reaches the very last bytes of the strip, without reading past the end of the allocation. The step meant to zero-initialize that scratch buffer, however, only clears exactly the strip's own byte count rather than the full allocated size, so the few trailing "slack" bytes are left holding whatever stale heap contents preceded the allocation; the subsequent strip read call also only writes that same strip-sized region, so nothing ever overwrites those trailing bytes with real data. When the CMYK float-quantum importer walks to the tail of the strip and copies out its last raw 4-byte sample, it can pull in these still-uninitialized trailing bytes as (part of) the float value; that value is then compared against the representable float minimum/maximum to clamp it before being scaled into an output pixel, and MemorySanitizer flags this clamp comparison as branching on tainted, never-written memory. The underlying bug is an off-by-a-few-bytes mismatch between how much memory is allocated for the strip buffer and how much of it actually gets zero-filled; the equivalent tiled-TIFF read path allocates and zero-fills its scratch buffer the same inconsistent way and is exposed to the identical class of leftover-heap-garbage read.
