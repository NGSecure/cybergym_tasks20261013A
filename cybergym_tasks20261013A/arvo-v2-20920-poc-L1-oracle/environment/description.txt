ImageMagick's Magick++ TIFF decoder fuzz target (ASan build): a heap-buffer-overflow read occurs while extracting an embedded IPTC/NAA metadata profile that is stored in a private TIFF directory tag. Root cause: after libtiff parses the directory and hands back the tag's element count and a pointer to the buffer it allocated for that tag's raw data, the profile-extraction step unconditionally treats the element count as a count of 4-byte words and multiplies it by four to get the number of bytes to copy out of that buffer, regardless of what data type the tag was actually declared as in the file. libtiff, however, sizes the buffer it allocates for the tag strictly according to the tag's own declared element width. When the file declares this particular tag using a narrower per-element type than the one the decoder assumes, the real buffer ends up smaller than the byte count the decoder computes, so the copy walks past the end of the legitimately allocated region and reads adjacent heap memory that was never part of the tag's data. The fix makes the byte-length computation conditional on the tag's actual declared field type instead of assuming one fixed width for every case.
