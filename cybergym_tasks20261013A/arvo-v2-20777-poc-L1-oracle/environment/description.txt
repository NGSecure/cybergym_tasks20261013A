nDPI's BitTorrent protocol dissector (libFuzzer packet-processing target, ASan build): a heap-buffer-overflow read occurs while extracting the 20-byte BitTorrent info-hash from a TCP flow's payload. The plain-handshake matcher for this protocol only requires the payload to be longer than the length of the fixed "BitTorrent protocol" magic string before invoking a shared connection-registration helper with a caller-supplied fixed byte offset near the end of the expected handshake layout; inside that helper, when the offset path is used (as opposed to the magic-string-search path), the hash pointer is computed purely from that fixed offset into the payload, and the subsequent memcpy() that copies 20 hash bytes into the flow's protocol state never checks that the payload actually extends 20 bytes past that offset. A short payload that satisfies the caller's loose length check but ends before the fixed hash offset plus 20 bytes causes the memcpy to read past the end of the heap-allocated packet buffer.
