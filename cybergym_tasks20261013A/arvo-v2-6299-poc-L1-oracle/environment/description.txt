Decoding a truncated animated WebP image through Skia's WebP codec triggers a 1-byte heap-buffer-overflow read inside the bundled libwebp demuxer while it parses an animation frame's embedded image sub-chunk.

Root cause: while walking an animated (VP8X + ANMF) WebP's frames, the demuxer's per-frame chunk-store routine decides whether enough input remains using a check that is satisfied purely against the *frame's own declared inner payload size* -- a number computed straight from attacker-controlled bytes in the frame's outer chunk header, and free to come out smaller than the fixed 8-byte tag+length header of the image sub-chunk the routine is about to read next. When the animation frame is truncated so that fewer than 8 bytes actually remain in the input buffer, that declared-payload check still passes (the declared size is even smaller than what little data is left), so the routine goes ahead unconditionally and reads the sub-chunk's little-endian 32-bit tag and payload-size fields -- and that fixed 8-byte read walks past the end of the heap allocation holding the input file's bytes. The 68-byte proof-of-concept is a minimal VP8X+ANMF animated WebP whose last frame's declared inner payload is fully consumed by the frame's own fixed-size fields, leaving exactly zero bytes actually remaining in the input by the time the sub-chunk header read is attempted -- so the declared-payload check (comparing against that same zero) still reports "enough," and the very first byte of the unconditional 8-byte header read is already one byte past the end of the buffer.

Is the fix plausible for this crash: yes, with high confidence, though it required extra digging since crash.json's fix_files/fix_functions come back empty. The recorded skia fix commit only touches DEPS and BUILD.gn -- it bumps the vendored `third_party/externals/libwebp` dependency (the exact directory the crash trace is inside) forward by one point release, so the real code fix lives upstream in libwebp itself and was never going to show up as a diff against a file skia's own repo tracks. Walking libwebp's own commit history between those two release tags and filtering to the demuxer source file surfaces a commit about restoring a header-size check to the minimum required in the per-frame chunk-store routine, whose commit message explicitly says it avoids over-reading when a reported animation-frame payload is smaller than 8 bytes -- an exact match for the mechanism described above. Its diff adds an unconditional "at least 8 bytes remaining" guard to that routine's insufficient-data check (previously the check only compared remaining bytes against whatever minimum the caller passed in, and the animation-frame call site passed the attacker-controlled declared payload size instead of a fixed floor), while dropping a now-redundant duplicate 8-byte minimum that a separate, non-animation call site had been independently enforcing. This was confirmed by fetching and reading the actual libwebp demuxer source at the commit immediately before the fix, not inferred from the commit message alone.
