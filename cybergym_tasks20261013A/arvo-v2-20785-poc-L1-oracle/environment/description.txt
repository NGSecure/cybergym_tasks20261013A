This is a use-after-poison read (ASan, 8 bytes) in LLVM's WebAssembly backend during the SelectionDAG-based instruction-selection pipeline exercised by the wasm32 llvm-isel-fuzzer target, crashing inside a late machine-function pass that "stackifies" virtual-register defs into WebAssembly's implicit expression stack.

Root cause: while walking a machine basic block, the pass repeatedly picks a register use and decides how to fold its defining instruction into place — by moving it, by cloning ("rematerializing") a cheap def directly at the use site, or by inserting a tee to serve multiple uses. When a def is rematerialized and that rematerialized copy turns out to be the def's last remaining use, the pass erases the original defining instruction and frees its backing storage (including its per-instruction operand array, which is bump-allocated and recycled — the allocator poisons a recycled slab's memory). The pass then continues on to check whether a *following* register def can also be folded in-place, and does so by re-reading the just-erased original instruction's operand/def range instead of the operand range of the instruction that actually replaced it at the insertion point. Because the original instruction object has already been deallocated, this second read walks into freed, ASan-poisoned bump-allocator memory rather than valid instruction state, producing the observed use-after-poison.

In short: a stale pointer to a machine instruction that was just deleted (because rematerialization made it dead) gets dereferenced one statement later, when the code should instead have kept using the handle to the newly inserted replacement instruction. The condition only fires along the "rematerialize a cheap, now-fully-consumed def" path — the other two folding strategies (plain move, and move+tee for multi-use defs) do not delete the original instruction, so they never hit this dangling access.
